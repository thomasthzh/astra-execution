# 独立集成与交付

多份代码合到同一候选版本，或任务要求 PR/MR、CI、发布时读取。简单单文件修复不建额外流水线。沿用仓库已有分支、审查、CI 与发布约定；平台差异读 [git-forges.md](git-forges.md)。

## 集成入口

同一目标分支/候选版本由一个 integrator 串行处理。worker 可继续独立任务，但不同时推送、rebase 或修补集成候选。

核对实际 diff、用户验收、前置版本、验证和未解决项。跨模块/高风险改动采用独立审查上下文，给目标和真实产物，不只给实现者“已正确”的结论。先查需求实现，再查具体缺陷；不强制每项两轮形式化审查。

worker 报告是线索，不是独立证据。检查需求漏项、共享状态、失败路径和已有用户改动归属；只修当前目标相关的实质缺陷。若测试或判分逻辑也改变，单独检查其是否仍表达需求，不能仅凭新测试绿色验收。需要建立或诊断修复循环时读 [verification.md](verification.md)。

## 顺序集成

1. 从明确目标基线按依赖顺序接收已验收产物，沿用项目 merge/rebase/cherry-pick 策略，不反复叠加策略。
2. 冲突须理解业务语义。普通冲突由 integrator 处理，共享合同/目标冲突交 Astra；不自动选 ours/theirs。
3. 在集成候选上跑相关回归及项目必需检查。worker 分支绿色只证明该分支，不能标记合并结果绿色。
4. 保存候选提交与对应结果；有未提交增量时同时记录实际差异，不能只用 HEAD 标识被测内容。候选内容、重要依赖或环境改变后重跑受影响检查；其余可信证据复用，避免无关全套复测。
5. CI 失败先区分实现/交互、测试缺陷、环境/瞬时故障、规格缺失。把可定位的失败证据交回 owner；仅因新修复、新假设或识别出的瞬时故障重试。测试有误须保留原始失败和修订依据；工具/授权阻塞不能靠再开 agent 解决。

有 merge queue / GitLab merge train 时服从队列及当前候选的必需检查；没有队列也不能以旧 head 绿色证明新 head。GitLab merged-results/train 验证的是合成提交，应核对其与当前源/目标的关系，不能机械要求 pipeline SHA 等于源分支 SHA。不绕过保护规则、删测试或改验收来制造通过。

## 外部动作与重放

实现、开 PR、合并、推送、安装、发布是不同结果。按用户请求/已有授权推进到对应终点，不自动捆绑全部，也不重复询问已授权动作。

- 外部目标不明时，先做可审查改动、候选版本和验证，再询问剩余具体决定。需权限时说明实际来源与被阻动作。
- 创建 issue/PR/release/deployment 前查记录和远端事实；请求后存返回 ID。超时先核对是否成功，避免重复创建。幂等键仅使用服务实际支持的机制，不能靠本地文字声称幂等。
- 创建 GitHub PR 后按 Codex 宿主要求调用 `attach_artifact`。GitLab MR 仅在工具明确支持时附件化，不把仅支持 GitHub 的工具强行用于 MR；保留其完整链接即可。描述围绕最终行为、验证与真实风险；开 PR/MR 成功不等于合并成功。
- 需部署时记录版本、目标、结果与必要上线验证。实际观测成功且满足要求后才报“已发布”。回滚按项目机制制定，不臆造通用命令。
- CI/环境不可用时保留候选，说明缺失证据与解除方式，不伪造通过。

## 吞吐与结束

READY_TO_INTEGRATE 持续积压时先降低实现并发，优先集成关键依赖和最小完整改动。共享锁文件、迁移顺序、公共 API 由指定 owner 负责。

验收和用户要求的交付动作有真实证据后结束。可记录额外建议，但不把未经请求的改进扩张成新项目。
