# 验证循环

当任务涉及多项可观察需求、跨模块约束或反复失败的检查时按需读取。此文是选择和解释验证的工程建议；具体命令、必需检查与通过标准以项目和用户要求为准。本 skill 不自动提供测试运行器，也不使文字约定成为强制门槛：脚本与 CI 必须真实执行，结果才能作为执行证据。

## 先确定验收

- 把需求写成可观察的行为、边界或产物，并为每项指出已有检查或人工核对方式。用“需求 → 检查 → 证据”定位覆盖缺口；没有检查不等于需求已满足。
- 分开记录**硬门槛**与**优化指标**。硬门槛包括用户指定验收、项目必需检查和关键正确性约束，未满足不能报完成；性能、成本或体验目标只有在明确阈值与测量条件时才按阈值判定，否则记录比较结果与权衡，不把改善幅度冒充保证。
- 复用仓库已有测试命令、构建入口、CI 和发布检查。只增加能发现当前风险的局部检查；复杂的关键约束可由独立于实现路径的检查验证。保留专用评测用例适合比较实验或适用的高风险场景，不要求所有开发都维护隐藏测试。

## 局部修复与集成

1. 稳定复现的 bug，先记录触发条件和失败表现，再修复。新测试应检验需求而非复制实现；现有测试也可能写错，发现冲突时回到需求和产品事实核对，不为得到绿色而删断言、放宽评分或改验收。
2. 在受影响范围内运行最快且有区分力的检查；失败后形成具体假设、修复并重跑相关检查。依赖、共享接口或候选内容改变时，扩大到受影响的回归范围。
3. 集成者在最终候选版本上执行项目必需检查及跨模块验收。worker 的绿色结果不能证明集成候选；旧提交的绿色结果不能证明新改动。相关验收已通过且无具体风险时停止追加可选测试和打磨。

每次关键验证能追溯到**被测提交及工作区增量**；多轮修改时保存可定位的 diff/产物快照，涵盖相关未跟踪文件，不能只列一个反复变化的文件名。无 Git 的产物记位置和可辨版本。记录实际命令或操作、结果及证据位置，明确失败、未运行与原因。检查结果以工具输出和 CI 状态为准，不以代理自报替代。

## 失败分流

| 观察 | 下一步 |
| --- | --- |
| 产品缺陷：需求与行为不符 | 保留复现和失败证据，修实现，重跑受影响检查。 |
| 测试缺陷：断言或夹具与已确认需求冲突 | 先核对规格和实际行为，再修测试；保留修改理由和前后结果。 |
| 环境或瞬时故障：依赖、服务、资源或网络异常 | 核实环境与远端状态；仅在环境恢复或有瞬时故障证据时重试，不把未运行报为通过。 |
| 规格缺失：无法判断预期行为或阈值 | 收集选项及影响，升级给有权确定需求的人；独立部分继续推进。 |

同样的失败重复出现且没有新假设或新证据时，停止盲目重跑，缩小复现、检查日志和依赖，或升级诊断。诊断和重试受用户预算、项目成本与任务风险约束；不能靠耗尽预算换取偶然绿色。

## 可选轻量记录

任务包、CI 链接和交接已足够时直接复用；短任务不强制新账本。需要比较多轮候选时，可用 JSONL 每次追加一条，字段保持轻量：`task`、`candidate`、`check`、`result`、`evidence`、`next_action`、`failure_kind`。内容必须对应真实命令或工具结果。

```jsonl
{"task":"T2","candidate":"abc123 + work/T2/attempt-2.patch（本轮无未跟踪文件）","check":"npm test -- api.test.ts","result":"fail","evidence":"work/T2/attempt-2-test.log","next_action":"核对空输入预期","failure_kind":"待判定"}
```
