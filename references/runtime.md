# 宿主、模型与运行时

仅在搭建分派、隔离或恢复机制时读取。以下工具名来自 Codex 桌面环境；以当前暴露的 schema 为准。缺失时不要模拟调用或依赖不存在的服务。

## 子代理与聊天

同一目标的临时协作使用 `collaboration.spawn_agent`、`send_message`、`followup_task`、`wait_agent` 等原生能力。用户明确要求新聊天时才用 `create_thread`；它不是 worker 工厂。跨现有聊天协调须已有用户授权；未经授权不要向其他聊天或外部人员发消息。

- 给 worker 独立任务包、允许编辑的路径、共享资源边界。
- `fork_turns` 支持时，边界清晰任务用 `none` 或少量历史并补齐上下文；大量隐含信息不可替代时才继承全部。
- 宿主若禁止全历史 fork 同时覆盖模型，改用小上下文 fork 加明确模型，不重复提交非法参数。
- 模型以工具支持值为准，可用时采用 `gpt-6-sol` / `gpt-6-luna`。主代理保持用户选择，不能通过 role 文本“变成 Astra”。
- 对正在跑的工作发增量消息或跟进，不再启动一份副本。
- 子代理树共享并发预算。若只有 4 个总槽位，主代理 + lead + 2 workers 已满；通常主代理 + 2 workers + 按需 reviewer/integrator 更简单。10 个任务可分波次执行。
- 复用合适的 owner；旧历史干扰或需要独立审查时才用新上下文。不要用模型调用当定时器。

## Worktree 与共享副作用

分派代码写入前确认目录、Git 基线、用户已有修改和 owner。每个 worker 得到绝对工作目录与明确 base SHA；每次 shell 调用显式设置工作目录。仅在提示中写路径并不会切换工具执行目录。

1. Codex 桌面先 `list_artifacts`，复用适合且无人占用的活动 worktree。需新隔离时优先 `create_worktree`；异步创建完成后再使用真实路径。该工具不自动移动主聊天，未提交改动不自动复制。
2. 使用用户指定/项目真实目标分支和已核实 ref，不假设当前分支就是 main。记录 base SHA，给集成者保留候选版本位置。
3. 同 worktree 的不重叠编辑可并行，但 Git index、checkout、commit、merge、rebase 只由一个协调者操作。锁文件、生成文件、共享配置、端口、测试数据库也是写入资源。
4. Worktree 只隔离检出文件，不隔离端口、凭据、远程数据库或部署目标。相同副作用的操作串行，或使用明确隔离的测试资源。
5. 依赖任务使用前置产物对应基线，或先合入前置提交；若按固定合同先做消费者，声明 mock 边界，并在真实依赖可用后验收端到端行为。
6. 无 worktree 工具时遵守宿主规则，允许才用原生 Git。无隔离且文件重叠就串行。非 Git 任务按文件所有权分派，不强加分支流程。

回收前确认无人/无进程依赖，改动已交付或已保存。托管 worktree 用 `archive_worktree` 保存可恢复快照，重要 ignored 文件另行保留；不要删除目录代替归档，不因 PR 合并就回收仍在用的 checkout。不为日常新任务恢复旧归档。

## 持久状态与恢复

复用项目已有 issue、任务板和执行记录，避免两套真相。没有时在 `work/astra/<run-id>/state.md` 存简短账本（路径按项目约定调整），由主代理或唯一 lead 写。worker 返回证据，由 owner 入账；大输出写到其独有结果文件，只回传摘要和路径。

账本不是定时器、锁服务或持久进程。外部动作前保存意图/目标，之后记录返回 ID、状态、产物与提交。恢复时与 Git、工具状态、远端事实对账，再继续，防止重复开 issue/PR 或发布。

多机器/多个独立控制器抢任务，需要任务系统实际支持的原子 claim、版本检查或锁；普通 Markdown 不提供原子抢占。没有则指定单一调度者，不伪称分布式并发。

## 等待与后台

活动运行中优先等 agent/CI 状态变化，超时读紧凑状态。遵守宿主等待上限和更新频率，不照搬“两三小时才唤醒一次”。

过夜/跨轮继续必须有实际宿主机制。仅当用户要求定时、持续监控或稍后继续时使用 `automation_update`；先查已有自动化，避免重复。默认 thread heartbeat，明确独立作业才另建 cron。提示词保存目标、账本位置、验收、停止条件；状态未变时安静，仅通知实质变化、完成、失败或需要输入。完成后按工具能力结束或停用相关监控，避免空转。

无排程能力则保存 checkpoint，说明需要恢复；不能承诺聊天结束后仍在运行。本 skill 安装不创建自动化、不改账户配置。

## 效率判据

关键路径短、同一接口冲突或集成积压时减少 worker；独立长调查/模块较多时再增加。集成积压先消化，不继续制造未验收分支。

比较验收通过率、总耗时、人工介入、返工/冲突、可归因用量和后续遗漏。每个验收任务的成本 = 全部尝试的模型/工具成本 ÷ 验收任务数；失败尝试、协调与集成都计入，无验收任务时报告总消耗而不作除法。时间与费用分别记录，账户共享用量无法归因时写未知。

切模型、提高 effort、加代理都应解决观察到的质量/速度瓶颈。先使单任务验证循环可靠，再扩大并行；集成和验收跟不上时，加 worker 不算有效吞吐。

仅在用户要求评估模型/流程收益时做对照：用同一组代表任务、起始版本、工具权限和最终验收，记录模型/effort、运行日期及预算口径；将反馈修复、模型替换与组织变化分开比较。需要比较时可先测 Sol/Astra × 单次提交/反馈修复，再对最佳单模型方案加入协作。最终评分保留未参与循环的检查，所有方案接受同样评测；按预算比较通过率，并同时报告成本、耗时和波动。小样本只作试点，不用增加轮次后的裸分宣称普遍胜出，不为日常交付自动启动评测工程。
